# Visual freedom and production safeguards

Effective 2026-10-04. This policy supersedes mandatory HDK adoption for the ten registered dashboard projects.

## Visual freedom and production safeguards

The project owns its frontend design. `.hermes-dashboard.json` → `uiPolicy` is the
current acceptance policy and supersedes older mandatory HDK/tier/layout rules.
Claude may change the shell, navigation, colors, typography, CSS, component library,
and frontend framework. HDK remains optional; its adoption score is not release readiness.

Keep experiments in `prototypes/` or `design-prototypes/`, outside production
static roots and navigation. These are development-only, never proof of production
readiness. Promoting a prototype requires integrating its data and auth contracts.

Run `npm run dashboard:standard:check` for admission. Preserve backend authentication,
API/data semantics, action permissions, and functional tests. Before production use,
run `npm run dashboard:release:check`: it requires reviewed, current-revision evidence
for build, auth, API contracts, workflows, accessibility, desktop/mobile layout,
data states, prototype isolation, and production proof. Do not manufacture evidence
or treat an admission pass as release approval. Existing project tests/builds still apply.

Do not run shared-kit sync/migration to restore a previous design. Visual asset sync
is manual and requires an explicit project selection and `--apply-visual-sync`.
Legacy HDK checks are available as `dashboard:hdk:check` for optional kit adoption;
their component names, CSS hashes, or tiers do not govern a project-owned frontend.

## What remains enforced

Admission validates route ownership, proof/health endpoint declarations, platform data
states and workflow declarations, proof capture tooling, and existing backend/proof
boundary checks. It does not prove that the running app works. Existing build/test,
auth, permission, data-freshness and action safety checks remain required.

Prototype roots must live outside production static/app roots, under `prototypes/`
or `design-prototypes/`. Do not link or import them into production. The metadata gate
rejects production registry URLs/surfaces pointing into those roots; release evidence
must also prove they are not served. No comment or filename alone grants an exemption.

Production designs may use any framework, custom CSS, tokens, layout or component
library. Update route manifests when files/routes change. HDK adoption and old T3C
scores describe that library only; they cannot grant or deny production readiness.

The CSS/token scans report kit differences as advisory for project-owned designs.
Legacy manifests retain strict HDK enforcement. Kit source tests remain required for
changes to the shared library itself. Shared asset writers skip project-owned projects
unless explicitly selected with `--project <id> --apply-visual-sync`.

## Commands

- Project admission: `npm run dashboard:standard:check`
- Project release: `npm run dashboard:release:check`
- Fleet admission (hub): `npm run dashboard:ui-policy:fleet`
- Fleet production evidence (hub): `npm run dashboard:release:fleet`
- Fleet ship check: retains source-readiness and build-budget checks, then runs neutral production evidence.
- Optional historical kit diagnostics: `npm run dashboard:hdk:check`; hub aggregate versions are named `dashboard:hdk-legacy:*`.

The broad `dashboard:standards:summary*` and `dashboard:standards:validate-all*`
commands now mean admission, not deployment approval. Dedicated HDK certification
commands still measure HDK conformance; do not use them as project-owned UI release gates.

## Production evidence

Store real review evidence at `uiPolicy.releaseEvidence` (default
`docs/design/ui-release-evidence.json`). No passing evidence is generated by migration.
The gate requires a reviewed source commit with no outstanding source changes, evidence
matching the latest source-changing commit and project, and a timestamp within seven days.
Proof-only commits are excluded from the source revision to avoid a self-referential hash. Review artifacts
may be added under `docs/design/ui-proof/` after the source commit.

The JSON record uses `schemaVersion: 1`, `projectId`, `revision`, `generatedAt`,
`stage: "production-candidate"`, `reviewedBy`, and `checks`. Every check contains
`status: "passed"` and a project-relative `artifact` pointing to actual nonempty evidence.
Required check names: build, authentication, api-contracts, workflows, accessibility,
responsive-layout, data-states, prototype-isolation, production-proof.
`screenshots.desktop` and `screenshots.mobile` point to captured screenshots.

This is an evidence admission gate, not a browser test runner or independent verification
of the contents of reports. The reviewer and existing CI suites must establish the
underlying behavior. Prototype screenshots, fabricated reports, and old screenshots
must never be recorded as production proof. No previous tier label is promoted by this change.

## Existing pipelines

Khashi CI keeps its build/tests and backend checks, while exact navigation labels,
kit imports and component-registry diagnostics are no longer required CI steps.
Its deployment preflight additionally requires the neutral production evidence gate.
Existing project `release:check` commands now also require this gate. The shared fleet
ship command uses it. Deployments outside these entrypoints must call the release gate
explicitly; this change does not modify remote GitHub protection or production hosts.
